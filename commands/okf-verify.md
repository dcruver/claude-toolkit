---
description: Walk this repo's unconfirmed OKF concepts with the user - read each draft or drifted one against its source, ask, and stamp the ones they confirm with okf verify --by human:<id>. Stops before rewriting a word of prose.
argument-hint: [path ...] (optional - narrow the walk to these concepts or sources; omit to take the whole unconfirmed queue)
---

Turn this repository's unconfirmed concepts into reviewed ones. Everything else in the OKF workflow writes prose; this command writes none. What it produces is one `verified` entry per concept a **human being** actually read and confirmed, which is the only thing in the bundle that no automated run is allowed to manufacture — and the reason the rest of the workflow is safe to run unattended at all. So the rules below are mostly about the difference between a review and a record of one.

**1. Settle the bundle, then the queue**
- The bundle root is the **current directory**, not the repo toplevel. Check `git rev-parse --show-prefix`; if it is not empty, `cd` to the toplevel and run from there unless the user explicitly asked for a bundle in this subtree. Use that one root for **every** call below: with no `okf.json` beside it, `okf` answers from its built-in defaults rather than failing, so a call against the wrong directory reports on a bundle nobody configured and never says so. Name the root in the report.
- No `okf.json` at the root means this repo is not a bundle yet and there is nothing to confirm. Stop and send the user to `/okf-init`.
- **The draft half of the queue.** Sweep the concepts themselves — `okf list` walks *sources*, and half of what needs confirming is not beside one: a `<stem>.<TypeName>.md` sibling from a multi-type file, and every higher-order concept under `docs/`, are concepts `okf list` will never name. A concept is a `.md` that opens with `---` on line 1, closes on a later line that is exactly `---`, and carries SPEC.md §4 fields; take the ones whose first top-level `status:` is `draft`. Read the **first** such line and not the last, because that is the one `okf`'s own reader takes, and a concept carrying two disagrees with itself in the direction the shell has already chosen.
  - Sweep the **work tree**, not the index: `git ls-files --cached --others --exclude-standard -- '*.md'`. A plain `git ls-files` misses everything `/okf-generate` wrote and nobody has staged yet, which is precisely the batch most likely to be sitting here waiting for a human. `--exclude-standard` is what keeps the sweep out of gitignored trees.
  - `--exclude-standard` honours `.gitignore` and nothing else, so hold the sweep to `okf.json`'s `include` and `exclude` globs as well. A concept sitting in a vendored or build tree is out of the bundle's scope by a decision somebody already made, and `okf check` will never report it drifted however stale it gets — so walking one puts a question to the user that no later run will ever ask again, about a file the bundle does not claim to describe. Higher-order concepts under `docs/` are the deliberate exception: they are in the bundle without being under an `include` glob, because they describe no source.
  - Leave `index.md` and `log.md` out at every level. The first is `okf index`'s own generated listing — `type: Codebase` at the root, `type: Package` below it — and the second belongs to OKF's semantics; neither is prose anybody wrote, so there is nothing in either for a human to confirm.
- **The drifted half.** `okf check` prints one `<kind>: <path>` line per finding, and `drifted: <concept>` is the one that belongs here — the concept stores a `code.content_hash` that its `resource` no longer hashes to. A `missing: <source>` line and an `orphan: <concept>` line are not this command's, and step 5 says where each goes. **Read stderr as well**, and keep it apart from stdout: a concept whose stored `code.content_hash` is not `sha256:` and 64 lower-case hex characters, or whose `resource` cannot be read, is warned about there and left off the `drifted:` list entirely, because no comparison was made. Take its exit status seriously in one direction only — plain `okf check` is **always 0 when it ran at all**, whatever it found, so a 1 means the run could not start (no git work tree, an `okf.json` that will not parse) and is an error to report rather than a clean bundle.
- **Then subtract what is already confirmed**, by SPEC.md §8's rule rather than by `status`. A concept is already Human-reviewed when it carries a `verified` entry whose `by` begins `human:`, whose `at` is not earlier than `generated.at`, and which is not drifted. Asking the user to confirm one of those again spends the only attention this command has on a question that has an answer. Two consequences worth stating, because they are what makes the tier the right filter and `status` the wrong one:
  - A **Tier 0** concept never leaves `status: draft` — SPEC.md §5 fixes it there — so a queue built on `status` alone would offer every stub back for ever, however many times it had been read. What keeps a confirmed stub out is its `verified` entry.
  - A concept at `status: stable` with no human entry behind it is still unconfirmed, and it is in the queue if it drifted. `stable` is somebody's judgement about the prose; the trust tier is a fact about the record.
- The two halves overlap: a concept can be `draft` *and* drifted, and it is one entry in the queue with both reasons attached. Dedupe by concept path.
- `$ARGUMENTS`, when given, **narrows the walk to concepts already in the queue** — it never adds one. Resolve each argument against the directory the user typed it in and rebase it on the bundle root before matching, since step 1 may have `cd`'d. Match it as either half: an argument naming a concept matches directly, and one naming a *source* matches every queued concept whose `resource` is that source, which is how a multi-type file is asked for. Match a directory as a path prefix *with its trailing slash* — `src/route/`, so it does not also swallow `src/routes/`. An argument matching nothing is usually a concept that is already confirmed and not in the queue, which is the ordinary case and not an error: say which it is and move on. An argument naming a concept that is already Human-reviewed is the one case where re-confirming is legitimate, because the user asked for that concept by name — see step 3 on what a second entry means.
- If `okf` is not installed **or cannot run** — its preflight exits 1 naming the SPEC.md §3 tools it is missing, and `jq` and `rg` are hard requirements — the documented fallback is to do this by hand rather than to stop. The drifted set is every concept whose stored `code.content_hash` differs from `sha256sum < <resource>` — on stdin, so the filename it would otherwise append stays out of the value — with `sha256:` in front of the bare hex. Step 3 says how to append the entry without the tool. Print a note that you are running without `okf`, and do not write a second implementation of it into the repo.

**2. Order the walk, and hold it to what the user can actually read**
A confirmation is a person reading a concept against its source. That is minutes of somebody's attention per concept, and it does not scale by being asked for faster.

- **Highest value first.** Take `code.tier: 2` and the high `code.fan_in` counts ahead of the rest: a wrong hub concept misleads every reader who arrives through it, and a wrong stub misleads the one person who opened it. Fan-in is a **ranking signal for where documentation effort goes, never a correctness claim** — it counts a name — and ranking a review queue is exactly what it is for.
- **Present the queue before walking it**, as counts by reason and by tier, and say roughly how long it is. A user who can see forty concepts coming can decide to do six today, which is a good outcome; one who finds that out at concept thirty cannot.
- **Show both texts.** Per concept: the concept's frontmatter facts that a reader trusts without opening the file — `code.symbol`, `code.lines`, `code.signature`, `code.members` — the body, and the source it names. Read the source yourself first and say plainly what you think, including where you think the concept is wrong. That is analysis offered to the reviewer, and it is useful; it is not the review, and step 3 says why.
- **Ask, and take only an answer.** One concept, one question, and a yes that names the concept. Do not read a confirmation out of `continue`, `looks good so far`, `next`, or silence. A blanket "they are all fine" is the user's to give and is a real answer — record in the report that it was given as a batch, so the shape of the review is visible in what the run says it did.
- **Stop whenever they want to.** A half-walked queue is the normal outcome and not a failure: the concepts nobody reached stay exactly as they were, and Unverified is an honest resting state. There is nothing to clean up.

**3. Stamp what the user confirmed — `okf verify`, once per concept**

```
okf verify <concept> --by human:<id>
```

- `<concept>` is SPEC.md §5's concept ID, the bundle-relative path minus `.md`, and the path itself is accepted too, since §5's whole point is that the two are the same fact. That is what lets `okf check`'s own `drifted:` lines be passed straight back in without editing them. What it does **not** accept is SPEC.md §4's bundle-absolute form: a `resource` value or a link target starts with a `/` that means the bundle root and not the filesystem's, and paths here are read as the filesystem's. `okf` says so and names the other spelling rather than guessing.
- **Always pass `--by`, and always spell it `human:<id>`.** Without it the actor defaults to `human:` and `$USER`, `$LOGNAME` or `id -un` — the account this session happens to be running as, which is a claim about *who reviewed this* answered by a fact about a process. Ask the user which id is theirs if it is not already obvious from the session, and put that in. The prefix is load-bearing and nothing else in the string is: SPEC.md §8 reads an entry as a human's **only** when its actor begins `human:`, so `--by human/dcruver` is not a spelling slip but a review that silently does not count. `okf` warns about an actor outside §4's vocabulary on stderr and then records it as given, so that warning is one to read and act on rather than pass along.
- **One concept per run.** It refuses a list, deliberately — a run over several would have to decide what to do about the third when the second could not be written. Loop, and check the status of each.
- **Read the two lines it prints.** `verified <concept> by <actor> at <instant>` on stdout says what landed, and `trust: <tier>` on the next line is SPEC.md §8's answer for the concept as a whole afterwards: `Unverified`, `Machine-confirmed` or `Human-reviewed`. That tier is the question the user is actually asking, so put it in the report per concept. It is read back out of the concept and not out of the entry just written, which is why a `--by process:okf/0.2` on a concept a human reviewed yesterday still says Human-reviewed.
- **The exit status is not the tier.** A run that appends the entry exits 0 whatever the tier comes out as — the record was asked for and the record is there; the tier is what it is worth. So a `trust: Machine-confirmed` is a successful run reporting a disappointing answer, and the explanation for it goes to stderr, next to the tier and not instead of it. A non-zero status means no entry was written at all, and step 4 says what that means for `status`.
- A `trust: Human-reviewed` **with a note on stderr** is a weaker claim than a silent one: it means drift could not be ruled out — the `resource` could not be read, or its digest could not be taken — so the tier stands on a comparison nobody made. Report the note with the tier.
- **A second entry is a second review, not a correction.** Entries accumulate and are never merged or replaced, so verifying a concept twice records two readings at two instants, which is what actually happened. Never re-run `okf verify` because the tier did not come out as you hoped: the tier is a property of the concept, and a second identical entry changes none of the things it is computed from.
- Without `okf`, append the entry by hand in SPEC.md §4's shape, at the indentation the existing entries already use — `- by:` and `at:` on the entry's own two lines, with `at` under `by` — with `date -u +%Y-%m-%dT%H:%M:%SZ` for the instant, and open a `verified:` block immediately above the closing `---` when there is none. Never merge into an existing entry, and work the tier out by hand from §8's rule rather than reporting none.

**Drift is a bar to confirming, and this is the one place the walk says no.**
A drifted concept's body was written against a version of its `resource` that is gone. There is no reading of "I have read this and it is correct" that survives not knowing which source it was correct about, so the answer is `/okf-refresh` first and this command afterwards — the refresh sets `status: draft` and moves `generated.at`, which puts the concept back in this queue with prose somebody can actually confirm. Show the drift, say that, and move on.

Stamping it anyway buys nothing, and it is worth being exact about why rather than leaving it as a preference. SPEC.md §8 degrades the concept to **Machine-confirmed** for as long as the drift stands, so the entry earns nothing now; and when `/okf-refresh` repairs it, `generated.at` moves past the entry, so the entry cannot earn the tier later either. It is a record with no reading under which it counts. If the user, told that, still asks for one — they read the concept and the source, the change was a comment, and the fact of their having read it is theirs to record — write it and report the `Machine-confirmed` it comes back with. Never on your own initiative.

**4. Settle `status`, in the same pass and only after the entry landed**
A confirmed concept left at `status: draft` comes back in tomorrow's queue, so the promotion is what makes the walk finite.

- `status: draft` → `status: stable`, on a concept the user confirmed and whose `okf verify` exited 0. **In that order**: a concept marked `stable` with no entry behind it is a claim nobody made and is invisible to every later walk, which is the one mistake here that hides itself.
- **Except at Tier 0**, where SPEC.md §5 fixes `status: draft` and it stays there. Its `verified` entry is what keeps it out of step 1's queue, which is why that queue is built on the trust tier rather than on this field.
- A concept the user did **not** confirm keeps every byte it has. There is no "rejected" entry in OKF and inventing one would be inventing a field; the record is that it is still `draft`, still unverified, and named in the report with what the user said about it.
- **Never touch `stale_after`.** It is `okf check --stamp`'s mark at the instant drift was detected, and this command resolves no drift. Deleting it here would clear the signal without fixing what raised it.
- **Carry every other key across untouched** — `title`, `tags`, `sources`, `generated`, all of `code:`, and anything OKF or a later version of this toolkit added that you do not recognise. An unrecognised key is somebody's data, not noise. In particular `generated.at` and `generated.by` do not move: you wrote nothing.

The layout is a contract, not a preference — the shell reads these files with `awk`, so a concept that is valid YAML but laid out differently is one `okf check` and `okf verify` can no longer see, and a `status` edit that broke it would take the concept out of the workflow it was just confirmed into. Keep the file opening with `---` on line 1 and closing on the next line that is exactly `---`; top-level keys unindented as `key: value` with **no tabs anywhere**; `code:` and `generated:` on bare lines of their own with their scalars at exactly two spaces and list items at four; and `verified:` exactly as `okf verify` left it, its dash and keys at the columns it used. Rewrite the one `status:` line in place and nothing else — no reflow, no reordering, no requoting of values you did not write.

**5. Report, and say what is still unconfirmed**
Confirmations are the small half of what this run produces. The queue that is left is the other half, and it is what somebody plans the next session around.

**Report**, concise: the bundle root; the queue as it stood, by reason and by tier; per concept walked, what the user said, whether an entry was written, and the `trust:` tier `okf verify` reported with any note it came with; every concept promoted to `stable`, and every Tier 0 one left at `draft` on purpose; the concepts still in the queue and why each is there; concepts sent to `/okf-refresh` for drift, with what changed under them; the `missing:` and `orphan:` findings you left alone; anything `okf check` warned about on stderr; and whether the walk was finished or stopped part way.

Then leave alone, and name, what this command deliberately does not repair:
- **Drifted concepts.** `/okf-refresh`'s, per step 3.
- **Missing concepts.** An in-scope source with no concept beside it is `/okf-generate`'s. There is no body here to read, so there is nothing to confirm.
- **Orphans.** A concept whose `resource` is gone needs either a corrected `resource` or a deletion, and both are decisions about intent. Deleting one destroys its `verified` history, which nothing can reconstruct. Name it with what you think happened to its source.

Stop there. Explicit non-goals for this command:
- **No confirming on the user's behalf.** You having read the concept and the source and found them to agree is analysis, and it belongs in the report; it is not a human review and it may not become a `verified` entry. This is the whole point of the command existing separately: SPEC.md §11 keeps `ralph/<model>` off a verified entry entirely so that unattended regeneration is safe precisely because it cannot forge review, and a slash command stamping `human:` for a person who never answered would forge the same thing by hand. Never pass `--by claude-code/<model>` or `ralph/<model>` here either — that records a machine confirming a machine's prose, which is a line in a file and not a fact about anything.
- **No prose, and no fixes.** A concept the user says is wrong is reported, not corrected. Rewriting it and then confirming your own correction in the same walk collapses the two halves of the workflow into one, and there is no reviewer left. `/okf-refresh` re-authors what drifted; `/okf-generate` writes what was never written.
- **No editing, reordering or removing an existing `verified` entry.** SPEC.md §8 calls them historical facts: an entry records that a named actor said they had read this concept at an instant, and nothing can make that not have happened. Only `okf verify` appends one.
- **No `okf check --stamp`.** Plain `okf check` is the one read-only report in this workflow, and this command has no reason to make it a write.
- **No `okf index` run.** No concept is added or removed here, so no per-directory index is out of date because of it.
- **No source edits.** Reading the code to review a concept never becomes fixing the code. Note what you found and move on.
- **No editing `okf.json`.**
- **No Tier B**: no chunking, no embeddings, no Qdrant.
- **No commit.** Leave the stamped concepts in the working tree, so the diff of what was confirmed is there to read.
