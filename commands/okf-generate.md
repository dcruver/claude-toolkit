---
description: Author OKF concept files for this repo's undocumented in-scope sources - read each file, extract its declared types, tier them from okf fanin and size, and write the co-located .md beside each. Stops before verifying anything.
argument-hint: [path ...] (optional - narrow the run to these files or directories; omit to take everything okf list --missing reports)
---

Document this repository's in-scope source files as OKF concepts. `okf` decides *which* files and supplies the numbers; this command reads the source, decides the tier, and writes every word of prose. That split is the whole design — see the division of labour below — so do not reach for the shell to parse code, and do not reason your way around a number the shell gave you.

**1. Settle the bundle, then the work list**
- The bundle root is the **current directory**, not the repo toplevel. Check `git rev-parse --show-prefix`; if it is not empty, `cd` to the toplevel and run from there unless the user explicitly asked for a bundle in this subtree. Use that one root for **every** call below: with no `okf.json` beside it, `okf` answers from its built-in defaults rather than failing, so a call against the wrong directory reports on a bundle nobody configured and never says so. Name the root in the report.
- No `okf.json` at the root means this repo is not a bundle yet. Stop and send the user to `/okf-init` — opening a bundle is that command's job, and the scope it settles is the thing worth looking at before any effort is spent here.
- `okf list --missing` is the work list: in-scope sources with no concept file beside them. Take it verbatim.
  - If it prints nothing, check the exit status before reading anything into it. Non-zero is a failure to report — a malformed `okf.json` is the usual cause and it says why on stderr — not an empty repo. A clean exit with no output has two causes that look identical, so run plain `okf list` before choosing between them. Output there means every in-scope source already has a concept. With `$ARGUMENTS` given, carry on anyway — a fully documented bundle is exactly the state the raised-tier deepen is asked for in. Without them there is nothing to generate, and re-authoring the ones that drifted is `/okf-refresh`'s job, not this command's. *No* output there means the bundle's scope is empty — globs or extensions matching nothing, or sources git does not track — which is a misconfiguration to report, not a documented repo. Say which it is and stop.
- `$ARGUMENTS`, when given, **narrows the run to paths that are already in scope** — it never pulls in one that is not. Resolve each argument against the directory the user typed it in, then rebase it on the bundle root before matching — step 1 may have `cd`'d to the toplevel, and a relative path carried across unchanged names a different file or none. Then match against plain `okf list`, not just `--missing` — and match a directory as a path prefix *with its trailing slash* — `src/route/`, so it does not also swallow `src/routes/` — since `okf list` prints files only and a bare directory would otherwise be reported out of scope while every file under it is in it: an argument naming an in-scope file that already has a concept is how a user asks for step 5's raised-tier deepen, which is the one case that touches an existing file, and holding the arguments to `--missing` alone would make that case unreachable. An argument matching nothing in `okf list` is usually out of scope — a decision to respect rather than route around — but check `git ls-files --others --exclude-standard` before saying so — not `git status --porcelain`, which collapses a wholly-untracked directory to a single entry and so never names the file inside it: scope comes from `git ls-files`, so a source git has never been told about is invisible to `okf` however well it matches the globs. That one needs a `git add`, which is the user's call, not an exclusion. Name it either way, with which of the two it is. Without arguments the work list is exactly `okf list --missing`.
- If `okf` is not installed **or cannot run** — its preflight exits 1 naming the SPEC.md §3 tools it is missing, and `jq` and `rg` are hard requirements — SPEC.md §3's documented fallback is to do the same work directly rather than to stop: scope is `git ls-files` filtered by `okf.json`'s `include`, `exclude` and `extensions`, then by SPEC.md §5's own exclusions — symlinks, files deleted from the work tree, and anything carrying a `@Generated`-style annotation. Do not re-filter through gitignore: `git ls-files` has already applied it, and a force-added file is tracked and therefore in scope, so a second pass would drop a source `okf list` reports. the digest is `sha256sum < <path>` — on stdin, so that the filename it would otherwise append, backslash-escaped when the name is awkward, stays out of the value — with a `sha256:` prefix added to the bare hex, and fan-in is `rg --no-config --no-ignore --case-sensitive --fixed-strings --word-regexp --text --count-matches --no-filename` summed across those files — without `--no-filename` ripgrep prefixes each count with its path and the output cannot be summed as a list of numbers — excluding the file whose stem is the type name only when exactly one in-scope file has that stem, as `okf fanin` does — exclude it unconditionally and an ambiguous stem tiers differently from the way `okf` would. Count *matches* and not lines — plain `--count` reports one per line and quietly understates every name used twice on a line, which would tier the file differently from the way `okf fanin` does. Print a note that you are running without `okf`. Do not write a second implementation of it into the repo.

**2. Read each source once, and extract its declared types on that pass**
`bin/okf` never parses source code and never will. Reading the file to document it is the only pass over it, so pull everything the frontmatter needs while it is open.
- `<stem>` throughout is the filename with its **final** extension removed, which is how `bin/okf` derives it: `parser.spec.ts` has the stem `parser.spec`, not `parser`. Taking `parser` would put the concept where `parser.ts`'s belongs and leave `parser.spec.ts` on `okf list --missing` for good.
- **One concept per declared top-level type.** A file declaring one type gets `<stem>.md` beside it. Where a file declares several, the first one — or the one sharing the file's name — takes `<stem>.md`, and each additional type takes `<stem>.<TypeName>.md` in the same directory.
- **Inner and nested types are documented inside the enclosing type's file**, under its `# Methods` or its prose, not in files of their own. The exception is a nested type that is both `public static` (or that language's equivalent) *and* referenced from outside the enclosing file: that one earns its own concept.
- A file with no declared type at all — a script, a module of free functions — still gets exactly one concept at `<stem>.md`, `type: Module`, or `type: Function` when it exports a single function.
- **Never write a concept over its own source.** `bundle.extensions` may name `md`, and `notes.md` derives `notes.md`: writing it would destroy the file you just read. `has_concept` guards this on its side and so must you — skip such a source and report it.
- **A source whose stem is `index` or `log` is skipped, not renamed.** Those two `.md` names are reserved — the per-directory `type: Package` index, and OKF's own `log.md` — and `okf list --missing` really does report `src/core/index.ts` and `src/core/log.ts`, so this comes up in any TypeScript repo. Writing `<stem>.md` would destroy the directory's index, which `okf index` then regenerates over the top, and the source would stay on `--missing` regardless. Do not invent a name for it either: `bin/okf`'s `has_concept` will not match `<stem>.<TypeName>.md` for this case, because such a name is indistinguishable from the concept of a sibling source called `<stem>.<TypeName>.<ext>`, so the file would be written and the source would *still* be reported as undocumented on every run. SPEC.md does not settle what this concept is called, and this command is not the place to decide. Skip it, and list it in the report as a known gap needing a name in SPEC.md.
- **Two sources sharing a stem in one directory** — `helper.ts` beside `helper.py` — collide on `<stem>.md` the same way, and the collision is silent: once one of them has the file, `okf list --missing` reports the other as documented too. Document whichever is on the work list first, skip the other, and name it in the report rather than letting it disappear. The reverse case costs the same and is easier to miss: a secondary type's `<stem>.<TypeName>.md` is indistinguishable from the concept of a sibling source actually named `<stem>.<TypeName>.<ext>`, so writing one can mark that sibling documented without a word having been written about it. Check for such a sibling before choosing the name, and report the clash instead of writing over it.
- Pick `type:` from the code vocabulary: `Class`, `Interface`, `Enum`, `Record`, `Struct`, `Trait`, `Function`, `Module`, `Package`. The higher-order kinds (`Service`, `API Endpoint`, `Architecture Decision` and the rest) belong to hand-written concepts under `docs/` and are not for this command.
- Record, per type: the fully-qualified symbol, kind, visibility, the line range, the declaration signature, what it extends and implements, and each member's name, signature and line range. Those become the `code:` fields, and going back for them later means reading the file twice.
- Never write a concept for a file you did not actually read. A plausible description inferred from a filename is the one failure mode this whole format exists to prevent.

**3. Ask the shell for the numbers**
- `okf fanin <Name>` per declared type name, for `code.fan_in`. A source with no declared type has no name to count, so leave `code.fan_in` out rather than inventing one — and with it out, neither fan-in trigger for Tier 2 can fire, so such a file reaches Tier 2 only on `loc >= tier2_min_loc`. Say so in the report when it lands a module at Tier 1 that felt bigger than that. It is a whole-word, case-sensitive, fixed-string ripgrep count of *matches* across the in-scope files. What it removes is not the declaration site but the whole file whose stem equals the name, and only when exactly one in-scope file matches that stem — so a type declared in a file named after something else, and every secondary type in a multi-type file, keeps its own self-references and reads high. Ties break high by design. Treat it as **a ranking signal for where documentation effort goes, never a correctness claim** — it counts a name, so it over-counts a common one and misses aliased imports. Do not adjust it by reasoning about imports, do not substitute a number you like better, and do not propose a parser to "fix" it; that design was considered and rejected, because a resolver that also matches by name is the same signal with more machinery in front of it.
- `okf hash <path>` for `code.content_hash`. It already carries the `sha256:` prefix — store the line verbatim, quoted. This is the value `okf check` compares against later, so a hash taken from anything other than the file you just read makes the concept drift-blind from birth.
- `git rev-parse --short HEAD` for `code.commit`. It fails in a repo whose sources are staged but never committed, which is a state `git ls-files` still returns a full work list for; leave `code.commit` out entirely there rather than inventing a value.
- `loc` for the tier rules below is the type's own line span, not the file's length — except for a source with no declared type, where the file *is* the concept and its own line count is the span. Its member count, for the Tier 0 rule, is the number of things it exports.

**4. Assign the tier**
Read the thresholds from `okf.json`'s `tiers` block — `tier0_max_members`, `tier0_max_loc`, `tier2_min_fan_in`, `tier2_min_loc` — rather than assuming the defaults. They are per-repo settings, and a repo that tuned them did it to move exactly this decision. A `tiers` block that is absent or partial is legal, and no `okf` subcommand reads it — the thresholds exist for this command, so filling in what the file leaves out is your job, key by key. The defaults `okf init` writes, and the ones to assume for any key that is missing, are `tier0_max_members: 2`, `tier0_max_loc: 15`, `tier2_min_fan_in: 8`, `tier2_min_loc: 200` — written out here because `SPEC.md` lives in `claude-toolkit` and not in the repo you are running in, so it is not there to look them up in. Use them for whatever the file does not set, and say in the report which four values you actually applied.
- **Tier 0 (stub)** — frontmatter, signature and links, no prose. When the type is a pure exception or marker (extends an error type, adds no members); or has at most `tier0_max_members` members *and* at most `tier0_max_loc` lines; or is a pure data holder with no logic and no doc comment — unless its fan-in or size would otherwise earn it Tier 2, in which case see the ordering note below.
- **Tier 2 (deep)** — Tier 1 plus `# Invariants`, `# Failure Modes` and `# Examples`. When `fan_in >= tier2_min_fan_in`, or `loc >= tier2_min_loc`, or the type is exported and `fan_in >= 4`.
- **Tier 1 (standard)** — everything else, and the default.

Those tests overlap, and SPEC.md §5 does not order them, so: apply Tier 2's first — fan-in exists precisely to send effort where the code is used, and a small type referenced across the repo is a hub whose invariants are worth writing down. Two kinds of type are exempt, and they are exempt differently. A pure exception or marker with no members stays **Tier 0** at any fan-in: `# Methods` over no members is a heading with nothing under it. A pure data holder with no logic caps at **Tier 1** instead of rising to Tier 2 — a widely-used one has earned the `# Schema` section Tier 1 already gives it, but `# Invariants` and `# Failure Modes` over a struct that cannot fail would be prose written to fill a heading. When a case genuinely sits on the line, take the higher tier and say in the report which files those were.

Two things the tier is not:
- **Tier 0 is a demotion, never an exclusion.** Every first-party declared type gets a file, so the concept graph stays total and no link into it dangles. A type is never skipped for being small.
- **A re-run never lowers a tier.** If a concept already carries an explicit `code.tier` above what these rules compute, that higher number wins — raising `code.tier` by hand is how a user asks for more depth, and silently overwriting it would throw the request away. It is one of only two cases in which this command writes to a file that already exists — the other being an interrupted write; step 5 says how both work.

**5. Write the concept beside its source**
The concept file goes in the **same directory** as the source. Its concept ID is its bundle-relative path minus `.md`, so the ID, the path and every link target are one fact.

**Do not rewrite a concept that is already there — with two exceptions.** Where a real concept already exists, the answer is normally to skip it, name it in the report, and leave it to `/okf-refresh`, which knows how to re-author a body that has drifted without losing what surrounds it. `okf list --missing` will not have offered you such a source; `$ARGUMENTS` still can.

The test is whether the file *is* a concept — opens with `---` on line 1 and closes on a later `---` — not whether something is sitting at that path, so read it and decide from what is in it. **A file that opens with `---` on line 1, carries only OKF frontmatter keys, and stops before a closing `---` is an interrupted write, and finishing it is what a re-run is for**: `has_concept` will not count it, so its source is still on `okf list --missing`, and `okf check` cannot see it either, which leaves `/okf-refresh` no way to reach it. Overwrite that one, and say in the report which files you overwrote on those grounds.

**Only that one.** Anything else at that path — prose with a hand-written header, a document ending its block with `...`, a file opening with `---` over content that is plainly not OKF frontmatter — is somebody's writing, and a README that happens to share a source's stem is the common case. It is never yours to overwrite, however much `has_concept` agrees it is not a concept. Report it and skip the source. Prose a person wrote is not recoverable from a report line saying it used to be there.

A partially finished multi-type file needs the same care from the other side. `has_concept` only ever looks for `<stem>.md`, so once that exists the source drops off `okf list --missing` even though its `<stem>.<TypeName>.md` siblings were never written. Write every concept a file owes in the one pass, and if you are here because `$ARGUMENTS` named such a file, the *absent* siblings are yours to write — they are missing concepts, not existing ones, and the skip rule does not cover them. The ones already there are covered by it as fully as any other concept: check each sibling path before writing, and skip the ones that exist. One of them may carry a `verified:` entry, and this is not the command that decides those are expendable.

The exception is the raised tier from step 4, and it needs both halves to be true: the concept's stored `code.tier` is **strictly above** the tier these rules compute, *and* its body is missing the sections that stored tier owes. Both, because either alone means something else — a body cut short at `# Collaborators` with `code.tier: 1` over a computed 1 is an interrupted write, not a request, and rewriting it here would be exactly the re-authoring this command does not do.

Where both hold, the number was raised by hand, and raising it is precisely how a user asks for more depth. Before touching it, check `okf hash` on the source against the stored `code.content_hash`, comparing the digests themselves — the stored value carries the double quotes this document requires on that field, and `okf hash` prints none, so a literal string comparison calls every concept drifted — passing the *filesystem* path, `src/route/RouteRegistry.java`, not the bundle-absolute `resource` value. `okf hash` reads paths as the filesystem's. It does not refuse a leading `/`, which is the trap: `/src/route/RouteRegistry.java` usually does not exist and it says so, but a `resource` that happens to name a real absolute path is hashed for real, and the digest of some unrelated file compares unequal and reports the concept as drifted. if they differ the concept is *drifted*, and deepening it would carry stale prose forward under a fresh hash, which erases the one signal `okf check` and `/okf-refresh` have. Leave a drifted concept alone and report it. Otherwise deepen it: add the sections the higher tier owes, update `generated.at`, take `generated.by` for yourself — you wrote the new sections, so a concept left stamped `ralph/…` or another model would mis-attribute them — drop any `stale_after` a previous `okf check --stamp` left behind — you have just confirmed the hash matches and rewritten the body, so leaving it would ship fresh prose marked stale — and **carry every other key across untouched, `code.content_hash` included**, since the source has not moved and the stored digest is already right. Above all leave `verified:` exactly as you found it. Those entries record a human having read this text, nothing can reconstruct one, and `okf verify` is the only thing that may ever write one. Moving `generated.at` past a `human:` entry does drop the concept from Human-reviewed to Machine-confirmed — that is correct, not a bug to work around: the review covered the old body and you have just written new sections into it. Set `status: draft` as part of the same edit, for the same reason — a concept left at `stable` never appears in the queue `/okf-verify` walks, so the demotion would be a number nobody acts on. Say so in the report, so whoever reviewed it knows it is back there. Never lower a `code.tier`, and never cut a body down to match a lower computed tier.

The frontmatter layout is a contract, not a preference: the shell reads these files with `awk`, so a concept that is valid YAML but laid out differently is one `okf check` cannot see. Every file this command writes must:
- open with `---` on line 1, and close on the next line that is exactly `---`;
- keep top-level keys unindented, as `key: value`, with **no tabs anywhere**;
- put `code:` on a bare line of its own, its scalars indented exactly two spaces and its list items exactly four, and give `generated:` the same two-space shape — the shell reads `generated.at` and `generated.by` by that same rule;
- leave any `verified:` block exactly as it is. It is not `code:`-shaped: SPEC.md §4 and `okf verify` both put its dash at two spaces with the entry's keys at four, and the shell reads `verified[].at` by relative indentation. This command never writes one, so the only rule it needs is to copy an existing block across byte for byte;
- write no inline flow mapping for a block the shell reads. `generated: {by: …, at: …}` satisfies every bullet above and is perfectly good YAML, and `generated.at` is then invisible to `okf`. The trust tier only compares a `human:` entry against a `generated.at` it can read, so the concept does not lose Human-reviewed — it keeps it unconditionally, including long after the prose was rewritten under that review. The check stops running and says nothing;
- use no multi-line or folded scalars — no `|`, no `>` — in any field.

The skeleton, with only the keys you actually have:

```yaml
---
type: Class
title: RouteRegistry
description: One sentence, on this line, saying what it is for.
resource: /src/route/RouteRegistry.java
tags: [routing, cache]
status: draft
generated:
  by: claude-code/opus-5
  at: 2026-08-27T14:02:11Z
code:
  language: java
  symbol: com.kairos.route.RouteRegistry
  kind: class
  visibility: public
  lines: [28, 214]
  signature: "public final class RouteRegistry implements RouteSource"
  extends: []
  implements: ["/src/route/RouteSource"]
  members:
    - {name: register, signature: "public void register(Route)", lines: [66, 88]}
  fan_in: 14
  tier: 2
  content_hash: "sha256:9f2a…"
  commit: "0b94c63"
---
```

Field by field, where it is easy to get wrong:
- `resource` is **bundle-absolute**, with a leading `/`, and keeps the source's extension: `/src/route/RouteRegistry.java`. It names the source, so every concept a multi-type file owes carries the *same* `resource` — `<stem>.<TypeName>.md` included. Deriving it from the concept's own filename instead names a file that does not exist, which puts the concept on `okf list --orphans`, a listing people act on by deleting things. `okf list` prints repo-relative paths, so add the slash.
- `implements`, `extends` and every link in the body are bundle-absolute too, but they point at **concepts, not sources**, so they carry the concept ID — the path with `.md` dropped, `/src/route/RouteSource`. Adding a slash to `okf list`'s output gives you `/src/route/RouteSource.java`, which resolves to nothing; every link written that way dangles. Resolve a referenced type to its concept ID the same way you named its file in step 2 — `<stem>` when it is the file's first or same-named type, `<stem>.<TypeName>` when it is a secondary one — and note that the stem is the *file's*, which need not match the type name at all. If you cannot find where a referenced type is declared, leave the link out rather than guessing at a path: a plain name in the prose is honest, a dangling link is not.
- `resource` names the concept's own source file. `sources:` is for **external** references only — a ticket, an RFC, an upstream doc. It is never a restatement of `resource`; leave the key out when there are none.
- `generated.by` is `claude-code/<model>` with the model you are actually running as substituted in, as in `claude-code/opus-5` — not the literal `<model>`, and not `ralph/…`, which is for the unattended loop.
- `description` and `title` are plain unquoted scalars in the skeleton, which is only safe while they contain no `: `, no whitespace-preceded `#`, and start with no YAML indicator character. `description: Routes issue #86 events` reads as `Routes issue` — the rest is a comment — to every YAML parser and to `okf` alike, which strips it the same way. Nothing disagrees; the description is simply half gone, in the field a reader picks the concept by. A sentence like `Resolves routes: by room id` is invalid YAML to every reader but the shell's `awk`. Rewrite the sentence, or wrap the value in double quotes — never in a `|` or `>` block, which SPEC.md §4 forbids outright. The already-quoted fields need the matching care: a `signature` or a member signature containing a double quote — a string default argument is the usual way — ends the scalar early unless the quote is escaped as `\"`. Backslashes inside a double-quoted scalar double, too.
- `generated.at` is the current UTC instant in ISO 8601: `date -u +%Y-%m-%dT%H:%M:%SZ`.
- `status: draft` on everything written here. SPEC.md §5 requires it of Tier 0, and it is right for Tier 1 and Tier 2 too: nothing this command produces has been read by a human yet, and `/okf-verify` walks the draft set.
- **No `verified:` entry, ever, at any tier.** Only `okf verify` appends those, and only for an actor who actually reviewed the text. A generator that could stamp its own output as reviewed would make the trust tier mean nothing — which is exactly why the loop is allowed to regenerate prose unattended.
- No `stale_after` either. That is `okf check --stamp`'s to write, at the instant drift is detected.
- No `okf_version`. It is legal only in the bundle-root `index.md`.

The body headings are chunk boundaries, so they are structural — use these, spelled this way, and no others:

| Tier | Body |
|---|---|
| 0 | No body. Frontmatter, signature and links only. |
| 1 | `# Responsibilities`, `# Collaborators`, then `# Methods` with one `## <signature>` per member. `# Schema` instead of `# Methods` for a record or DTO. |
| 2 | Tier 1's, plus `# Invariants`, `# Failure Modes`, `# Examples`. |

Write about what the code does and why, at a level the source does not already state. A `# Responsibilities` section that paraphrases the class name is worse than a Tier 0 stub, because it looks like documentation.

**6. Say that the indexes need regenerating — do not regenerate them here.** `okf index` builds each `index.md` from the concepts `git ls-files` reports, and everything written above is untracked, so running it now would rewrite every index with not one of the new concepts in it. Tell the user in the report to run `okf index` once these files are committed. That ordering is the reason this command stops without committing rather than in spite of it.

**Report**, concise: the bundle root; how many files were in the work list and how many concepts were written; the breakdown by tier and by top-level directory; every file skipped and why (already documented, drifted, reserved or colliding stem, unreadable, argument matched nothing); the tier thresholds you actually applied; any type whose fan-in count you think is misleading, as an observation rather than a change; that `okf index` should be run once these files are committed; and that `/okf-verify` is where a human confirms this batch.

Stop there. Explicit non-goals for this command:
- **No `verified` entries and no verification.** This command cannot confirm its own output. `/okf-verify` walks the drafts with the user; that is a separate command for exactly this reason.
- **No re-authoring a concept that is merely out of date.** A body whose source has drifted belongs to `/okf-refresh`, which knows to keep the `verified` history a rewrite would otherwise destroy. Step 5 names the only two files this command may write over: a concept whose `code.tier` was raised by hand, which it deepens rather than replacing, and an interrupted write, which it finishes. Nothing else.
- **No source edits.** Reading the code to document it never becomes fixing the code. Note what you found and move on.
- **No editing `okf.json`**, including the tier thresholds. If the scope or the thresholds look wrong, say so in the report and leave the file alone: a scope decision made silently is one nobody reviews.
- **No parser, no tree-sitter, no compiled helper**, and no attempt to make fan-in exact. Both were considered and rejected on their merits.
- **No Tier B**: no `index` block, no chunking, no embeddings, no Qdrant.
- **No commit.** Leave the new concepts in the working tree for the user to read.
