---
description: Re-author this repo's drifted OKF concepts - run okf check, read every source that moved under its concept, rewrite what the change falsified, and restamp code.content_hash and generated.at without touching a verified entry. Stops before confirming anything.
argument-hint: [path ...] (optional - narrow the run to these concepts or sources; omit to take everything okf check reports drifted)
---

Bring this repository's concepts back into step with the code they describe. `okf` says which ones have moved and supplies the digest; this command reads the changed source and writes every word of the correction. It is the one command that edits prose somebody may already have reviewed, so the rules below are mostly about what a refresh must not destroy on its way past.

**1. Settle the bundle, then the work list**
- The bundle root is the **current directory**, not the repo toplevel. Check `git rev-parse --show-prefix`; if it is not empty, `cd` to the toplevel and run from there unless the user explicitly asked for a bundle in this subtree. Use that one root for **every** call below: with no `okf.json` beside it, `okf` answers from its built-in defaults rather than failing, so a call against the wrong directory reports on a bundle nobody configured and never says so. Name the root in the report.
- No `okf.json` at the root means this repo is not a bundle yet, and a drift report over defaults nobody chose is not worth acting on. Stop and send the user to `/okf-init`.
- `okf check` is the work list. It prints one `<kind>: <path>` line per finding and this command owns exactly one of the three kinds:
  - `drifted: <concept>` — the concept stores a `code.content_hash` that its `resource` no longer hashes to. **This is the work.**
  - `missing: <source>` — an in-scope source with no concept beside it. `/okf-generate` writes those; naming one in `$ARGUMENTS` does not make it this command's, because there is no body here to re-author.
  - `orphan: <concept>` — a concept whose `resource` is gone. Report it and leave it; step 5 says why deleting one is not yours to do.
- **Read its stderr as well as its stdout, and keep the two apart.** A concept whose stored `code.content_hash` is not `sha256:` and 64 lower-case hex characters is warned about on stderr and left off the `drifted:` list entirely — there was nothing to compare, so no comparison came out unequal — and the same goes for a `resource` that cannot be read, one that is not a regular file, and one `sha256sum` failed on. The first of those is real work wearing no label: that concept has never been comparable and will never be reported drifted again, so a run that reads only stdout leaves it wrong for ever. Treat a malformed `code.content_hash` as drift and refresh it like any other. The other three are facts about a file rather than about a concept — report them and move on; a fifo where a source should be is not a documentation problem.
- Take the exit status seriously in one direction only. Plain `okf check` is **always 0 when it ran at all**, whatever it found — "CI warns, never gates" — so a 0 with no output means a bundle with nothing to do, and 1 means the run found nothing because it could not start: no git work tree, an `okf.json` that will not parse. That is an error to report, not a clean bundle. Do not reach for `--strict` to tell those apart; it changes the status of a run that found drift and nothing else about it, and this command reads the listing.
- **Never run `okf check --stamp` here.** It writes `stale_after` onto every drifted concept at the instant it detects them, which is a signal for the consumers of a bundle nobody is about to fix; you are about to fix it, and step 4 deletes that field on the way through. Stamping and then unstamping in one run dirties files this command otherwise leaves alone, and turns the one read-only report in the workflow into a write.
- `$ARGUMENTS`, when given, **narrows the run to findings `okf check` already reported** — it never adds one. Resolve each argument against the directory the user typed it in and rebase it on the bundle root before matching, since step 1 may have `cd`'d. Then match it as either half of a finding: an argument naming a concept matches a `drifted:` line directly, and one naming a *source* matches every drifted concept whose `resource` is that source — which is how a multi-type file is asked for, since its concepts are named after types and not always after the file. Match a directory as a path prefix *with its trailing slash* — `src/route/`, so it does not also swallow `src/routes/`. An argument matching no finding is usually a concept that has not drifted, which is the ordinary case and not an error: say so and move on. The one exception is a concept the user names that stores no `code.content_hash` at all — see step 4.
- If `okf` is not installed **or cannot run** — its preflight exits 1 naming the SPEC.md §3 tools it is missing, and `jq` and `rg` are hard requirements — the documented fallback is to do the same comparison by hand rather than to stop. The drifted set is: every `.md` that `git ls-files` reports, that opens with `---` on line 1 and closes on a later `---`, whose `resource` names a file in the same directory as the concept, and whose stored `code.content_hash` differs from `sha256sum < <path>` — on stdin, so the filename it would otherwise append stays out of the value — with `sha256:` in front of the bare hex. Print a note that you are running without `okf`. Do not write a second implementation of it into the repo.

**2. Group the work by source, not by concept**
`okf check` reports concepts, and several of them can name one `resource`: SPEC.md §5 gives the first or same-named type in a file `<stem>.md` and each additional type `<stem>.<TypeName>.md`, and all of them carry the same `resource`. One edit to that file drifts every one of them at once.

Read the source **once** and correct all of its concepts on that pass. Refreshing one and leaving its siblings is worse than leaving all of them: the run comes back reporting progress, and the siblings stay drifted with bodies written against a version of the file nobody can now identify.

**3. Read the source, and re-author what the change falsified**
`bin/okf` never parses source code. The whole reason this is a slash command is that reading the file is the only way to find out what actually changed about it, and that reading is also what makes the new hash honest.

- `git diff` against the concept's stored `code.commit`, where it has one, is the fastest way to see what moved — but it is a shortcut into the file, not a substitute for it. The body has to be true of the source as it stands now, and a diff read alone cannot tell you that the section it did not touch was already wrong.
- Rewrite what the change made false, and **leave what is still true alone**. A refresh is not a re-generation: the prose that survives is prose that has been read and stands, and rewriting a `# Responsibilities` section into different words with the same meaning throws away whatever review it carried for no gain. Say in the report which sections you actually rewrote.
- Update the `code:` facts to what you just read — `lines`, `signature`, `members`, `extends`, `implements`, `visibility`, `symbol`, `kind`. These are the fields a reader trusts without opening the file, and a line range that is off by a refactor is worse than none.
- **Re-tier.** Call `okf fanin <Name>` again for `code.fan_in` and re-apply SPEC.md §5's rules against `okf.json`'s `tiers` block — `tier0_max_members`, `tier0_max_loc`, `tier2_min_fan_in`, `tier2_min_loc`, defaulting to `tier0_max_members: 2`, `tier0_max_loc: 15`, `tier2_min_fan_in: 8`, `tier2_min_loc: 200` for any key the file leaves out, since SPEC.md ships with `claude-toolkit` and not with the repo you are running in. A file that grew past `tier2_min_loc`, or a type the change made popular, has earned Tier 2's `# Invariants`, `# Failure Modes` and `# Examples`; add them. Fan-in is a **ranking signal for where documentation effort goes, never a correctness claim** — it counts a name — so do not adjust it by reasoning about imports and do not substitute a number you like better.
- **Never lower a tier, and never cut a body down to match a lower computed one.** A stored `code.tier` above what the rules now compute is either a deliberate raise or the record of a type that used to be a hub, and deleting `# Invariants` because this week's fan-in came out at 7 destroys written analysis to satisfy an arithmetic that was never meant to be run backwards. Tier 0 is a demotion and never an exclusion in the other direction either: a type that shrank still gets its file.
- **A concept nobody generated is edited, not rewritten.** No `generated:` block means a person wrote this by hand — the higher-order kinds under `docs/` are usually theirs, but a co-located one can be too. Correct the `code:` facts and any sentence the source has actually falsified, keep their wording everywhere it still holds, and stop for confirmation before rewriting a whole section. Name every such concept in the report. Prose a person wrote is not recoverable from a report line saying it used to be there.
- Two things the source can do that no listing will ever report, both of which you will see because you read the file and nothing else does:
  - **A type was added.** Its concept would be `<stem>.<TypeName>.md`, and `bin/okf`'s `has_concept` only ever looks for `<stem>.md` — so the source is not on `okf list --missing`, the absent concept is on no listing at all, and neither this command nor a later one will be offered it. Do not write it here: authoring a concept from nothing is `/okf-generate`'s, and it writes the absent siblings of a file named in its own arguments. Name the type in the report and say to run `/okf-generate <path-to-the-source>`.
  - **A type was removed or renamed.** Its concept now describes something that is not there, and it is not an orphan — `resource` still exists, so `okf check` will go on reporting it drifted for ever, against a file that no longer contains it. Do not delete it and do not repoint it at another type: it may carry `verified` entries, and both of those are the user's call. Report it and leave it as it is.

**4. Restamp the frontmatter — the two fields that move together**
`code.content_hash` and `generated.at` are one write. The hash names which version of the source this text was written against; `generated.at` is when it was written. Moving either alone is a false claim:

- A hash advanced past a body nobody re-read makes the concept **drift-blind for ever**. `okf check` compares nothing else, so from that moment on the concept reports itself clean while saying something untrue about the code, and there is no later run that finds it. This is the one irreversible mistake available here. **Never restamp a concept you did not read the source for**, however obviously cosmetic the change looked in the diff.
- A `generated.at` moved without the hash claims a rewrite against a source the concept still identifies by its old digest, and leaves the concept drifted anyway.

So, per concept, in one edit:

- `code.content_hash` — the output of `okf hash <source>`, stored **verbatim and quoted**: `content_hash: "sha256:9f2a…"`. Two traps, both of which produce a plausible wrong digest rather than an error. Pass the **filesystem** path, `src/route/RouteRegistry.java`, not the bundle-absolute `resource` value: `okf hash` reads paths as the filesystem's and does not refuse a leading `/`, so `/src/route/…` usually fails loudly but occasionally names a real absolute path and hashes some unrelated file for real. And take the hash **after** reading the source, from the same bytes; if anything rewrote the file in between, read it again. When you compare a stored value against `okf hash`'s output, compare the digests — the stored field carries the double quotes this document requires and `okf hash` prints none, so a literal string comparison calls every concept drifted.
- `generated.at` — the current UTC instant, `date -u +%Y-%m-%dT%H:%M:%SZ`.
- `generated.by` — `claude-code/<model>`, with the model you are actually running as substituted in, as in `claude-code/opus-5`. Not the literal `<model>`. You wrote the correction, so a concept left stamped with a previous author's actor mis-attributes it; `ralph/<model>` is for the unattended loop, which refreshes by these same rules and stamps itself.
- `code.commit` — `git rev-parse --short HEAD`. Leave the key out entirely if that fails rather than inventing a value.
- `status: draft`. The prose is new and no human has read it, and `/okf-verify` walks the drafts — a concept left at `stable` is a correction nobody is ever asked to confirm.
- **Delete any `stale_after`.** It is `okf check --stamp`'s mark, written at the instant drift was detected, and you have just resolved that drift: leaving it ships fresh prose marked stale, and because a stamp already in the past is never moved forward again, it stays that way for good.
- **Carry every other key across untouched** — `title`, `tags`, `sources`, and anything OKF or a later version of this toolkit added that you do not recognise. An unrecognised key is somebody's data, not noise.

**`verified:` entries are never removed, never edited, never reordered, and never added to.** SPEC.md §8 calls them historical facts, and that is exact: an entry records that a named actor said they had read this concept at an instant, and nothing — not a rewrite, not a hash, not this command — can make that not have happened. Copy the block across byte for byte. Only `okf verify` may ever append one, and only for an actor who actually reviewed the text, which is what makes unattended refreshing safe at all: a loop that could forge review would make the trust tier mean nothing.

What that costs is deliberate and is not a bug to work around. Moving `generated.at` past a `human:` entry drops the concept from **Human-reviewed** to **Machine-confirmed** under SPEC.md §8's rule, because the review covered the body you have just rewritten. That demotion is the correct answer and it is *why* the entry is kept rather than dropped: the record of who read what, and when, is what makes the demotion computable. Say in the report which concepts fell out of Human-reviewed, so whoever reviewed them knows they are back in `/okf-verify`'s queue.

A concept the user named that stores **no** `code.content_hash` at all is the one case outside the drift report. It has never claimed to describe a particular version of its source, so nothing reports it and nothing ever will; giving it a digest is legitimate only once you have read the source and confirmed the body against it, exactly as above, and it is a claim about a text you did not write. Do it when it was asked for, never as part of a sweep, and name it in the report.

The layout is a contract, not a preference — the shell reads these files with `awk`, so a concept that is valid YAML but laid out differently is one `okf check` can no longer see, and a refresh that breaks the layout hides the very drift it exists to report. Keep the file opening with `---` on line 1 and closing on the next line that is exactly `---`; top-level keys unindented as `key: value` with **no tabs anywhere**; `code:` and `generated:` on bare lines of their own with their scalars at exactly two spaces and list items at four; `verified:` exactly as SPEC.md §4 and `okf verify` write it, its dash at two spaces and the entry's keys at four. Write no inline flow mapping for a block the shell reads — `generated: {by: …, at: …}` is good YAML and makes `generated.at` invisible to `okf`, which then cannot tell that a human review predates the prose and leaves the concept on Human-reviewed for ever, silently. No multi-line or folded scalars, no `|` and no `>`, in any field. And mind the plain scalars: a `description` containing `: ` or a whitespace-preceded `#` is half gone to every reader, `okf`'s `awk` included, so rewrite the sentence or wrap the value in double quotes; inside an already-quoted `signature`, a double quote must be escaped as `\"` and a backslash doubled.

**5. Confirm the refresh, and say what you did not fix**
Run `okf check` once more. Every concept you refreshed should be gone from the `drifted:` lines, and every warning you acted on gone from stderr. This costs nothing and catches the failure mode that matters: a concept still reported drifted after a refresh means the digest you stored is not that source's — the wrong path was hashed, or the file changed under you — and it is the only chance to notice before the value is committed as the truth. Nothing needs staging first; `okf check` takes the set of concepts from `git ls-files` but reads their contents from the work tree, and every concept in this run was already tracked.

Then leave alone, and report, what this command deliberately does not repair:
- **Orphans.** A concept whose `resource` is gone needs either a corrected `resource` or a deletion, and both are decisions about intent — was the file moved, renamed, or genuinely dropped? Deleting the concept destroys its `verified` history, which nothing can reconstruct. Name each one with what you think happened to its source and let the user decide.
- **Missing concepts.** `/okf-generate`'s.
- **Concepts whose source could not be read or hashed.** Report the path and `okf`'s own reason for it.

**Report**, concise: the bundle root; how many concepts were reported drifted and how many you refreshed; per concept, which sections you actually rewrote and which you left standing; any tier that rose and what raised it; every concept that fell from Human-reviewed to Machine-confirmed; hand-written concepts you edited; types added or removed that no listing reports, with `/okf-generate <path>` named for the added ones; the `missing:` and `orphan:` findings you left for others, with what you think each orphan's source did; anything `okf check` warned about on stderr; and the result of the confirming re-run.

Stop there. Explicit non-goals for this command:
- **No `verified` entry, and no verification.** This command rewrites prose; it cannot confirm its own output, and it may not append an entry even for a concept whose body it barely touched. `/okf-verify` walks the drafts with the user.
- **No authoring from nothing.** A `missing:` source, and a type whose concept was never written, both belong to `/okf-generate`. The line is whether there is a body to correct.
- **No deleting a concept**, orphaned or describing a type that is gone. Report it; the deletion is the user's.
- **No source edits.** Reading the code to find out what changed never becomes fixing the code. Note what you found and move on.
- **No editing `okf.json`**, including the tier thresholds. If a threshold looks wrong now, say so in the report and leave the file alone.
- **No `okf index` run.** This command adds and removes no concepts, so no per-directory index is out of date because of it — and running it here would rewrite files this run has no business touching.
- **No `okf check --stamp`.** Step 1 says why.
- **No Tier B**: no chunking, no embeddings, no Qdrant.
- **No commit.** Leave the refreshed concepts in the working tree, so the diff of what changed under review is there to read.
