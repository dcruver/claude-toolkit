---
description: Answer a question from this repo's OKF concepts - run okf search --hyde-prompt, answer that prompt yourself, and search with the hypothetical concept body you wrote. Presents the hits grouped by concept with each one's trust tier, or falls back to a ripgrep sweep over the concept files when the bundle has no index block. Stops at a reading list.
argument-hint: [question] (what you want to find in this codebase - a sentence, not keywords; omit and you will be asked for one)
---

Find the concepts in this bundle that answer a question. The retrieval is HyDE, and the whole of that idea is in step 2: `okf` never calls an LLM, so it prints a prompt and **you** write the answer, and it is your answer rather than the question that gets embedded and searched with. The corpus is concept bodies, and a vector search matches what a text is *like* — a question is like other questions, and there are none in the collection.

`$ARGUMENTS` is the question. If it is empty, ask the user what they are looking for and stop; there is nothing to guess at here, and a search run on a question nobody asked spends an embedding to rank the collection against nothing in particular.

**1. Settle the bundle, and check that Tier B is on**
- `command -v okf` — if `okf` is not installed, stop and say so: it ships in `claude-toolkit`'s `bin/` and is installed by that repo's `install.sh`. Stop the same way if its preflight refuses — it exits 1 naming the SPEC.md §3 tools it is missing. There is no by-hand substitute for the vector search itself, and the sweep below is not one — it is a lesser thing reached from a different branch, the one where `okf` runs perfectly well and the bundle never opted in. Note that step 2 is exempt from the `curl` half of that check, deliberately: `okf search --hyde-prompt` reaches no endpoint, so it will print a prompt on a machine where the search in step 3 cannot run. Getting a prompt is therefore not evidence that the rest of this command will work, which is the other reason to settle the prerequisites here rather than by trying the first call.
- The bundle root is the **current directory**, not the repo toplevel. Check `git rev-parse --show-prefix`; if it is not empty, `cd` to the toplevel and run from there unless the user explicitly asked for a bundle in this subtree. A wrong root here does not fail loudly the way it does for the Tier A commands: run from a subdirectory that happens to carry its own `okf.json`, and the search goes to whatever collection *that* file names, reported as this repo's answer. Use one root for every call below — the concept paths step 4 opens are relative to it too — and name it in the report.
- **Search is Tier B, and Tier B is opt-in.** With no `index` block in `okf.json`, `okf` exits **2** with one line naming the six keys it wants — `index.repo`, `index.qdrant_url`, `index.collection`, `index.embedding_url`, `index.embedding_model`, `index.embedding_dim`. That is SPEC.md §7's 2 and deliberately not its 1: this is not a broken bundle, it is one that never opted in to semantic retrieval. Report the line as it was printed, and then take the **Fallback** below rather than stopping: the concepts are in the tree whether or not anything ever indexed them, and a bundle with no collection is not a bundle with no documentation. Adding the block, standing up a Qdrant and filling it are three decisions, all the user's, and none of them is a repair you can make on their behalf.
- The guard sits at dispatch, ahead of the subcommand, so it answers **`--hyde-prompt` too**: there is no half of this command that runs on a bundle without the block. Check for it before writing anything, rather than discovering it after you have composed a document to search with — and read that as what it is: the fallback replaces steps 2, 3 and 4 whole, rather than picking up after a prompt you have already answered.

**Fallback: no `index` block, so a ripgrep sweep over the concepts instead**

Everything here runs in place of steps 2, 3 and 4, and only when step 1 stopped on the exit **2**. With no collection there is nothing to embed a hypothetical body against, so there is no prompt to answer and no ranking to present. What there is is a tree full of concept files, and `rg` reads them.

- **Print the note before you print any result**, and put three things in it, because a sweep reported as a search is worse than no answer at all: this bundle has no `index` block, so nothing was embedded and no vector search ran; what ran instead was a literal ripgrep over the concept files, matching the words of the question as text; and a concept that answers the question in words other than the ones asked does not appear here at all. That last one is what makes an empty result mean something different from what it means in step 3 — here it is "no concept contains these strings", never "this bundle has no answer" — and it is why the note goes first rather than under the results, where it reads as a caveat on an answer the reader has already believed.
- **Sweep with the question's own words, and not with a hypothetical body.** Step 2's document is written to be embedded; `rg` matches text literally, so those invented sentences would match nothing, and the stray word of them that did match would be a word you chose rather than one the user asked about. Take the handful of distinctive nouns out of `$ARGUMENTS` — type names, method names, the vocabulary of the domain — and leave the connectives out, since `the`, `a` and `how` are in every concept in the bundle. Do not pass the question as one string either: no concept body contains the user's sentence.

```
rg --no-config --fixed-strings --smart-case --files-with-matches --glob '*.md' -e 'handler' -e 'route' -e 'dispatch'
```

- Run it **from the bundle root**, the one step 1 settled. One `-e` per term, which is an or — a file carrying any one of them is a candidate — and it is also what keeps a term beginning with a `-` from being read as a flag. `--fixed-strings` is what makes the note above true: without it every term is a regular expression, so a method name taken out of the question matches text that is not it (`route(String)` finds `routeString`, and `Map<String, Handler>` is three operators before it is a type), and a term carrying an unbalanced `(` or `[` does not fail to match — ripgrep exits **2** on it, which is a sweep that never ran reported as a bundle with nothing in it. `--files-with-matches` because what this produces is a reading list, exactly as step 4's ranking is. `--smart-case` so a term typed in lower case still finds `Router`, while one typed with a capital is held to it. `--no-config` because `RIPGREP_CONFIG_PATH` names a file on the user's machine that can put any flag it likes on that line, `--glob` and `--max-count` included, and a sweep silently narrowed by somebody's dotfile comes back looking like a bundle with nothing in it. Leave ripgrep's ignore handling alone: it skips what `.gitignore` skips, which is the scope `okf` reads out of `git ls-files` anyway.
- **Then drop whatever is not a concept**, by opening the files rather than by trusting the glob. SPEC.md §4 has every concept open with `---` on line 1, so a `.md` that does not is a `README.md`, a design document, or this repo's own notes, and it documents no source. Drop SPEC.md §4's reserved names as well — `index.md` links every concept in its directory and `log.md` is OKF's own — because both match whatever their neighbours match and answer nothing on their own. What is left is the co-located concept files, and each one's `resource:` is the source it documents, exactly as in step 4.
- **Say plainly that the order is not a ranking.** There are no scores here and nothing to sort by that would mean anything; `rg` prints files in the order it finished reading them. Choosing what to open first by how many of the terms a file matched is fair enough, and it is one sweep per term with the lists compared — not `--count-matches`, which counts how often the terms occur rather than how many of them do, and so puts the file that says one word six times above the file that says all three once. Either way it is coverage or frequency, never similarity: a concept mentioning all three terms in passing comes out above the one that is actually about the answer. Never present it as a ranking, and never print a score of your own invention beside it.
- **Read the trust tier off each concept's own frontmatter.** Step 4 had it from the payload; nothing here carries one, so it is SPEC.md §8's rule applied by hand — and it still belongs beside every concept you quote. No `verified:` entry at all is `Unverified`. Entries only by non-`human:` actors — `process:`, `claude-code/`, `ralph/` — are `Machine-confirmed`. A `human:<id>` entry whose `at` is no earlier than `generated.at`, on a concept that has not drifted, is `Human-reviewed`, and it degrades to `Machine-confirmed` when either half of that fails. Step 4's caveat holds here too and for the same reason: a concept whose drift could not be checked keeps the top tier without having earned it, so say which of the two you are looking at when you can tell.
- **`okf check` still works** — it is Tier A, it needs no `index` block, and step 4's reading of it applies word for word: plain, no `--stamp`, filtered down to the concepts you are about to quote. It is also what answers the drift half of the tier above, so run it before you grade anything.
- **A sweep finds files, never chunks.** Step 4's ranking could put a method beside its concept because `okf chunk` had split the body first; nothing here has, so a method is reachable only through the file that contains it, and a concept file is the smallest thing this fallback can hand back. Read the whole body before quoting a heading out of it.

Then report as below, saying in as many words that this was the sweep and not the search, and that the `index` block is what would replace it.

**2. Ask `okf` for the prompt, and answer it yourself**

```
okf search --hyde-prompt "<the question>"
```

- Pass `$ARGUMENTS` through as the question, as **one argument**. It prints a prompt on stdout and exits 0 having sent no request at all — no embedding endpoint, no Qdrant. That is the whole of `okf`'s part in HyDE, and printing it is not a step to skip on the grounds that you already know what it will say: it is the instruction actually in force in this checkout, and it carries the question back inside it so that what you answer is what was asked.
- **You are the reader it is printed to.** Do what it says yourself. Do not relay it to the user as a question for them, and do not hand it on to another tool: there is no LLM behind `okf`, which is exactly why the prompt exists as text rather than as a request.
- `--k`, `--repo` and `--type` are **refused** alongside `--hyde-prompt`, and it exits 1 saying so. Nothing is being searched yet, so they have nothing to narrow; they belong on the command line in step 3, which is the one place they do anything.
- What the prompt asks for, and it is worth being exact because it is the query: the body of the **one** concept that would answer the question — the documentation of the single type, module or service the answer lives in — under SPEC.md §4's body headings, and only the ones that bear on the question. Name the types, methods and fields you would expect this codebase to have, confidently and by name. A plausible name in the codebase's vocabulary lands near the right concept; a hedge, and "it is not clear from the question", land nowhere. Prose under headings and nothing else: no frontmatter, no code fences, no preamble, nothing about the prompt itself. A dozen lines is plenty.
- **Nothing you write here goes into the bundle.** It is a search key, embedded and thrown away. Do not create a file for it, and do not offer it to the user as documentation of anything.
- **Show the user the body you wrote**, in the report. It is the query, and a run that prints only the results leaves nobody able to tell a bad question from an empty corpus.

**3. Search with what you wrote**

```
okf search "$(cat <<'OKF_QUERY'
<the body you wrote>
OKF_QUERY
)" [--k N] [--repo R] [--type T]
```

- **A quoted heredoc, and not the double-quoted one-liner `okf` itself suggests.** The prompt in step 2 asks for `` ## `<signature>` `` headings, so the body you just wrote almost certainly contains backticks, and very likely a `$` or an apostrophe as well. Inside `"…"` the shell reads a backtick pair as a command to run and `$name` as a variable to expand: the query that reaches `okf` would be silently a different text from the one you wrote, and in the backtick case the shell runs whatever is between them first. `<<'OKF_QUERY'`, with the delimiter quoted, expands nothing at all — and the `"$( … )"` around it keeps the newlines, which a bare `$( … )` would collapse. Expect this form to ask the user for permission where the plain one-liner would not: `permissions.json` allowlists `okf search` by prefix, and a command line containing a substitution is not something a prefix rule can vouch for. Take the prompt. A search is read-only and the prompt costs a keystroke; a query the shell quietly rewrote costs a ranking that looks perfectly good and answers a question nobody asked.
- **One argument either way**, newlines and all. Two words unquoted are two queries and are refused: two rankings printed one after the other are a single ranking that is not one.
- **The body, not the question.** Passing `$ARGUMENTS` here instead is a working command that throws step 2 away and searches the corpus of documents with a sentence that is not one.
- The endpoint and the collection come from the same `okf.json` `okf embed` read, and are deliberately not on the command line: a query embedded by a different model, or searched against a collection filled by one, is a vector in a space the points are not in, and Qdrant answers it with nearest neighbours all the same — confidently, and wrongly.
- `--k` defaults to 10 and widens the search; `--repo` and `--type` narrow it, as a filter applied at the collection, so `--k` still means "k results" rather than "as many of the top k as happened to match". Reach for them when the ranking comes back full of near misses from the wrong repo or the wrong kind of concept, and say in the report which you used — a narrowed search is a different question from the one the user asked.
- Two outcomes that look alike and are not. **No results** is an answer: `okf search` warns on stderr, prints nothing on stdout, and exits **0**. Read it precisely, because it is narrower than "nothing was close enough": the search carries no score threshold, so Qdrant returns the nearest points it has whether they are good or not. Zero of them means there were none to return — the collection is empty of anything matching, which with a `--repo` or `--type` on the line usually means the **filter** matched nothing rather than the query. Drop the filters and search again before reading anything into it. `--k` will not help here whatever `okf`'s own suggestion says: a larger limit on an empty answer is the same empty answer. A **404** from Qdrant is not this at all: it means there is no such collection, so no query would have worked and a better one is not what is wanted. `okf embed` is what creates and fills it — say so, and leave the running of it to the user, per the non-goal below. Report which of the two happened; never fold the 404 into "nothing matched", which would report an index that was never built as a bundle with no answer.

**4. Present it grouped by concept, with the trust tier on every one**

`okf search` prints the ranking already grouped — a concept header at column one, its hits indented under it:

```
kitchen  src/kitchen/Router  Class  Unverified  /src/kitchen/Router.java:6-26
  1.0000  summary  com.example.kitchen.Router
  0.9900  method  com.example.kitchen.Router#route(String)
```

- The header is `repo`, `concept_id`, `type`, **trust tier**, and the source it documents with its line range; each indented line under it is a matching chunk's score, kind (`summary`, `method`, `schema`) and symbol. A `-` is a field the payload does not carry, not a gap in the layout.
- **Keep `okf`'s grouping and `okf`'s order.** Groups are placed by their own best hit, so the first header names the concept the best hit is in. Do not re-rank, and do not flatten it back into a list of chunks: a method named on its own is an answer with its subject left out, and the concept above it is that subject.
- **Open the concepts before answering.** The ranking is a shortlist of documents, not an answer to the question. `<concept_id>.md` is the file; the located path with its leading `/` stripped — that `/` is SPEC.md §4's bundle root, not the filesystem's — is the source it documents. Read both, and answer from what they actually say.
- **A hit whose file is not there is a stale point, not a missing concept.** `okf embed` upserts, so a concept that has since been renamed or deleted keeps its points in the collection and keeps ranking. Say so and drop it from the answer — there is no prose behind it to read — rather than reporting the concept as one this bundle has. Do not go looking for the deleted file's content in git history to quote instead; whatever it said, nothing in the tree stands behind it now. And do not offer `okf embed` as the fix: it only upserts, `okf` has no delete path at all, and a re-run would leave the stale point exactly where it is. Clearing one means rebuilding the collection, which is nobody's job here — report it and move on.
- **The trust tier goes beside every concept you quote**, and it is the reason it is on the header rather than on the chunk: it grades the prose a reader is about to believe. SPEC.md §8's three are `Unverified` (nobody has confirmed it — very often a draft a model wrote), `Machine-confirmed` (verified, but only by non-human actors) and `Human-reviewed` (a person read it against its source after it was generated, and no drift was found against it then). Read that last one as the ceiling rather than a guarantee: "no drift was found" also covers "drift could not be checked", which is the tier a concept keeps when its `resource` cannot be read or its stored hash is malformed. `okf verify` says so on stderr when it stamps one; `okf embed` does not, and no payload field carries the note either, so in a ranking that case is indistinguishable from a clean review. `okf check` in the next bullet is the only way to tell them apart. Never present an `Unverified` body as fact; quote it and name the tier in the same breath, and say that the source beside it is the thing to check.
- **The payload is a snapshot.** `trust_tier` was stamped when `okf embed` ran, so a concept verified — or drifted — since is described by the ranking as it was then. Run `okf check` once, before you rely on any of it, and read its findings for the concepts in the ranking: `drifted:` means the body was written against a version of its source that is gone, so read it with the source rather than instead of it, and `orphan:` means the source is gone altogether. **Plain `okf check`, with no flags at all.** It takes no operand — naming a concept is refused — so it reports on the whole bundle and you filter its lines down to the concepts you are about to quote. It does take flags, and the one to stay away from is `--stamp`: that writes a `stale_after` into every drifted concept it finds, which turns this command's one read of the bundle into an edit of it. Read stderr too: a concept it could not compare is warned about there and appears on no findings line at all. And **take its exit status seriously in one direction only** — a plain run is always 0 when it ran at all, whatever it found, so a 1 means the run could not start (no git work tree, an `okf.json` that will not parse) and is an error to report rather than a bundle with nothing wrong with it. **It walks this bundle and only this bundle**, so a hit from another `repo` draws no finding of any kind — that silence is "not checked", not "not drifted", and reporting it as the latter would launder the one thing this bullet exists to surface.
- A `repo` on a header that is not this bundle's is a hit from another repo's points in a shared collection: SPEC.md §9 puts every repo in the one collection so that cross-repo search is a filter change. Those files are not in this working tree. Say which repo it is rather than sending the user to a path that is not there.
- **Settle what this bundle's own `repo` is before you call any hit foreign.** It is `index.repo` in `okf.json`, and where that key is absent it defaults to the **basename of the bundle root** — a checkout directory name, which need not be the project's. Do not work that fallback out by hand: `okf chunk <any concept in this bundle> | jq -r '.[0].repo'` prints the resolved value, the same one `okf embed` stamped on every point. It is a read that writes nothing, but `permissions.json` allowlists only `okf list`, `hash`, `fanin`, `check` and `search`, so expect it to ask — that is the second prompt this command can cost, after step 3's, and both are worth taking. Name it in the report, and use that value for `--repo` if the user wants the search held to this bundle. A derivation of your own that comes out wrong fails in two ways and both are silent: this repo's own concepts reported as somebody else's, and a `--repo` narrowing to a name no point carries — which comes back as "no results" and reads as an empty corpus.

**Report**, concise: the bundle root; the question as asked; the hypothetical body you searched with; the ranking, grouped and with tiers, as above; which of the concepts you opened and what they actually answered; anything `okf check` called drifted; the flags you narrowed with, if any; and — plainly — what the bundle turned out to have no answer for.

Stop there. This command's job ends at a reading list and the answer you can support from it. Explicit non-goals:
- **No answering from the body you wrote in step 2.** It is invented, and it was invented to be a search key. Every word of the answer comes from concepts and sources that are actually in the tree, and if the ranking supports no answer then that is the finding — a hypothetical document quoted back as documentation is the one failure mode this technique has, and it reads exactly like a good answer.
- **No writing or repairing concepts.** A concept the search turns up as wrong, thin or missing is reported. `/okf-generate` writes what was never written and `/okf-refresh` re-authors what drifted; neither is a thing to slide into from a query.
- **No `verified` entries.** Reading a concept to answer a question is not a review, and `/okf-verify` is where a human's confirmation is recorded, deliberately and with them present.
- **No `okf embed`.** It writes to Qdrant and re-embeds the bundle, which is a different command's cost and a different command's decision. An empty, stale or absent collection is reported here, not filled.
- **No editing `okf.json`**, and in particular no adding the `index` block the fallback stands in for. A Tier B configuration made silently is one nobody reviewed, and every later run inherits it.
- **No source edits.** Reading the code to answer a question never becomes fixing it. Note what you found and say so.
- **No `okf check --stamp`.** Plain `okf check` is the one read-only report in this workflow, and a command whose whole job is to answer a question has no reason to make it a write. Step 4 says what `--stamp` would write.
- **No commit, and no files.** This command writes nothing at all — not a concept, not a note, not the hypothetical body. The only output is what it says.
